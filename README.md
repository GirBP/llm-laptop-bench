# LLM Bench — browser edition

Український сайт для запуску мовних моделей **без встановлення програм**.

Сайт: **https://girbp.github.io/llm-laptop-bench/**

## Як користуватися

1. Відкрий сайт у настільному браузері. Почни з CPU / SmolLM2 135M або GPU / Qwen2.5 0.5B.
2. Вкажи назву ПК. Обери режим, модель, короткий або довгий текст і тривалість.
3. Натисни **Запустити тест**. Ваги завантажуються з Hugging Face, інференс виконується локально.
4. Завантаж JSON. Повтори **той самий тест** на другому комп’ютері.
5. Відкрий вкладку **Порівняння** й імпортуй обидва файли. Є експорт усіх вимірювань у CSV.

Моделі кешуються в браузері. Доступність WebGPU залежить від браузера, драйвера та GPU. Якщо WebGPU недоступний, сайт пропонує окремий CPU-тест; він не підміняє ним GPU-вимірювання. Користуватися сайтом можна без Git, Python чи Node.js.

## Межі висновків

Це порівняння **браузерного інференсу**, а не вимірювання максимальної продуктивності CUDA, Metal чи нативного CPU. Прямий гібридний поділ шарів, моделі 14B і MoE тут не реалізовані. Невдача браузерного запуску не означає неможливості запуску моделі через llama.cpp.

| Режим | Рушій | Моделі | Квантування |
|---|---|---|---|
| GPU / WebGPU | WebLLM 0.2.86 | Qwen2.5 0.5B, 3B, 7B | q4f32_1 |
| CPU / WASM | Transformers.js 4.3.1 + pinned ONNX Runtime Web | SmolLM2 135M, Qwen2.5 0.5B | ONNX q4 |

Це **різні файли ваг**. Сайт дозволяє порівнювати однаковий режим між ПК, але не розраховує перевагу між різними моделями/рушіями/форматами. FP32 у `q4f32_1` стосується обчислень; ваги квантуються до 4 біт.

Модельні ревізії, очікувані хеші файлів і незмінні URL GPU-бібліотек містяться в [site/models.json](site/models.json). Хеші файлів — метадані видавців; сайт не виконує незалежне повторне хешування всіх гігабайтів після завантаження. Різні ревізії мають різні URL кешу.

Швидкий профіль: 3 повтори по 64 нові токени. Тривалий: 5 повторів, щонайменше 20 хвилин повторних запитів, 5 повторів після прогріву, по 128 нових токенів. Є службовий запуск для ініціалізації поза статистикою. Кожний запит починається з нового KV-кешу. 20 хвилин не гарантують теплової рівноваги.

Тексти профілів сталі. Точна кількість токенів вимірюється й фіксується, а не вгадується з числа слів. GPU використовує контекст 2048/8192 і prefill chunk 512. У CPU контекст — перевірювана межа завдання; KV росте з фактичним текстом. Для всіх тестів batch=1, один запит одночасно, greedy generation.

GPU: PP/TG/TTFT беруться з `usage.extra` WebLLM. CPU: PP — кількість вхідних токенів / час першого `forward`; TG — `(generated - 1) / (last_token_time - first_token_time)`; TTFT — час до першого токена без завантаження моделі. Токенізація CPU виконується до таймера. Відмінність методик записана у звіт і блокує пряме зіставлення різних рушіїв.

Браузер не надає достовірної телеметрії системного swap, зайнятої VRAM/RAM, температури й потужності. Ці поля залишаються `null`. `navigator.deviceMemory` — грубий, обмежений браузером показник, не точний обсяг RAM. Ідентифікатор GPU може бути прихований. Для Razer треба перевірити, що браузер використав NVIDIA, а не Intel; Max-Q не визначається з однієї лише назви GTX 1060.

Звіти з фоновою вкладкою, помилками, перериваннями, різними ревізіями/протоколами чи неповними повтореннями не отримують коефіцієнтів переваги. Кількість WASM-потоків, версія браузера, адаптер і параметри зберігаються для оцінки налаштувань. Кількість потоків між ПК може різнитися; це порівняння налаштованих систем.

## Дані й кеш

Звіти зберігаються в `localStorage` поточного браузера та завантажених користувачем JSON. Немає серверного завантаження звітів чи аналітики. Інтернет потрібен для коду, шрифтів, WASM і початкового завантаження моделей. Постачальники хостингу/CDN отримують звичайні мережеві запити; тексти інференсу та звіти їм не надсилаються.

Для перенесення на інший ПК експортуй JSON. Очищення даних сайту видаляє локальні звіти та кеш. Вкладку слід тримати видимою. При перезавантаженні незавершений запуск позначається перерваним.

`site/isolate.js` — network-only Service Worker для заголовків COOP/COEP на GitHub Pages. Він не кешує запити та не встановлює локальних програм. Це дозволяє багатопотоковий WASM у сумісних браузерах. Якщо ізоляція недоступна, фактичне число потоків — 1, що фіксується у звіті.

## Розробка

Node.js 22+ потрібен лише для розробки/публікації сайту, не для відвідувачів.

```sh
npm ci --ignore-scripts --no-audit --no-fund
npm test
npm run build
npm run preview
```

Відкрий http://127.0.0.1:4173. При першому відвідуванні можлива одна перезагрузка сторінки для ізоляції WASM.

Опціональна браузерна QA з установленим Google Chrome:

```sh
UI_ONLY=1 node tests/browser-smoke.mjs
node tests/browser-smoke.mjs
RUN_GPU=1 node tests/browser-smoke.mjs
```

Другий тест завантажує ~181 МБ CPU-ваг і запускає справжній інференс. Третій додатково ~278 МБ GPU-ваг. QA-результати не є порівняльним набором продуктивності ноутбуків. Моделі 3B/7B та тривалий прогрів слід перевіряти окремо на цільових пристроях.

## Публікація

GitHub Settings → Pages → Source: **GitHub Actions**. Workflow `.github/workflows/pages.yml` запускає тести, складає статичний сайт і публікує `dist/` після push у `main`. Звіти, моделі та `node_modules` не потрапляють у репозиторій.
